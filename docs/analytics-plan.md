# Plan: Analytics (first-party, tanpa pihak ketiga)

Status: **fase 1 + 2 + pintu masuk owner diimplementasikan (lokal, belum di-deploy); fase 3 belum**

## Tujuan

1. Tahu berapa user yang benar-benar membuka Mini App, bukan cuma yang punya baris di `users`.
2. Tahu konten mana yang dilihat vs konten mana yang memicu reaksi/rating/komentar.
3. Tahu di langkah mana alur upload lewat bot putus.
4. Tahu berapa yang mentok di gate (channel / start bot) dan berapa yang lolos.
5. Semua angka bisa dibaca dari satu halaman internal `/stats` milik owner.

## Non-tujuan

- Tidak memakai Google Analytics / PostHog / Umami / pixel apa pun. Mini App
  dibuka dari Telegram; script pihak ketiga menambah berat dan mengirim data
  user ke luar.
- Tidak menyimpan IP, User-Agent, `initData` mentah, isi pesan, atau lokasi.
- Tidak menduplikasi data yang sudah ada di database (lihat bagian 3).
- Tidak membuat A/B testing atau heatmap di fase ini.

## 1. Prinsip

**Data yang sudah tersimpan tidak perlu dijadikan event.** `reactions`,
`ratings`, `comments`, `photos`, `notifications`, `leaderboard_announcements`
sudah punya timestamp dan user id. Event baru hanya untuk hal yang sekarang
hilang sama sekali:

- user membuka app (bukan sekadar ada di tabel `users`),
- foto benar-benar tampil di layar,
- gate ditampilkan / dilewati,
- langkah upload di bot,
- tombol share ditekan.

Dengan begitu tabel `events` tetap kecil dan angka engagement dihitung dari
sumber aslinya, bukan dari salinan.

## 2. Data Model

### 2.1 Tabel `events`

`src/db/schema.ts`:

```ts
export const events = pgTable(
  "events",
  {
    id: identity(),
    /** Nama event; divalidasi di app lewat union `EventName`, bukan check constraint. */
    name: text("name").notNull(),
    /** Null kalau user dihapus, atau kalau event terjadi sebelum login. */
    userId: bigint("user_id", { mode: "number" }).references(() => users.id, {
      onDelete: "set null",
    }),
    /** Null untuk event yang tidak terikat foto (app_open, gate, upload_step). */
    photoId: bigint("photo_id", { mode: "number" }).references(() => photos.id, {
      onDelete: "set null",
    }),
    /** Id acak per pembukaan app; dipakai untuk hitung unique view tanpa cookie. */
    sessionId: text("session_id").notNull(),
    /** Atribut kecil dan sudah diringkas; jangan simpan teks bebas. */
    meta: jsonb("meta")
      .$type<Record<string, string | number | boolean | null>>()
      .notNull()
      .default({}),
    createdAt: timestamp("created_at", { withTimezone: true })
      .notNull()
      .defaultNow(),
  },
  (table) => [
    index("events_name_created_idx").on(table.name, table.createdAt),
    index("events_created_idx").on(table.createdAt),
    index("events_photo_name_idx").on(table.photoId, table.name),
    index("events_user_created_idx").on(table.userId, table.createdAt),
    index("events_session_idx").on(table.sessionId),
  ],
);
```

Catatan desain:

- **Tanpa check constraint untuk `name`.** Daftar event akan tumbuh; constraint
  berarti migration setiap kali menambah event. Validasi cukup di TypeScript
  (`EventName` union di `src/lib/analytics/events.ts`).
- **`meta` jsonb, bukan kolom terpisah.** Tiap event punya atribut berbeda;
  jsonb menghindari tabel lebar yang 90% null.
- **Index sengaja banyak di awal.** Semua query dashboard memfilter
  `name` + rentang `created_at`. Kalau nanti terasa berat, index bisa dipangkas
  setelah rollup (fase 2).

### 2.2 Migration

Satu migration baru (`npm run db:generate` → `drizzle/0012_*.sql`):

```sql
create table events (
  id bigint generated by default as identity primary key,
  name text not null,
  user_id bigint references users(id) on delete set null,
  photo_id bigint references photos(id) on delete set null,
  session_id text not null,
  meta jsonb not null default '{}'::jsonb,
  created_at timestamptz not null default now()
);
create index events_name_created_idx on events (name, created_at);
create index events_created_idx on events (created_at);
create index events_photo_name_idx on events (photo_id, name);
create index events_user_created_idx on events (user_id, created_at);
create index events_session_idx on events (session_id);
```

Tanpa backfill: analytics mulai dari nol saat deploy. Data historis tetap bisa
dihitung dari `ratings` / `reactions` / `comments` (lihat bagian 6).

## 3. Katalog Event

| Event | Kapan dikirim | `photoId` | `meta` | Sumber |
|---|---|---|---|---|
| `app_open` | `POST /api/session` sukses, sekali per boot | – | `{ startParam, premium }` | client |
| `feed_loaded` | `GET /api/feed` selesai dan `photos.length > 0` | – | `{ count, pref }` | client |
| `photo_view` | kartu jadi aktif ≥1 detik (bukan saat prefetch) | ya | `{ index, media, nsfw, blurred }` | client |
| `nsfw_reveal` | user menekan "Tampilkan" / mematikan blur | ya | `{ always }` | client |
| `gate_shown` | gate channel tampil | – | `{ kind }` | client |
| `gate_pass` | `/api/subscription/check` bilang subscribed | – | `{ kind }` | client |
| `share` | tombol share ditekan | ya | `{ channel: "telegram" }` | client |
| `pref_change` | `PUT /api/preferences/gender` sukses | – | `{ pref }` | client |
| `upload_step` | bot pindah step upload | – | `{ step, media }` | bot |
| `upload_published` | `createPhoto` sukses | ya | `{ media, gender, nsfw }` | bot |
| `upload_abandoned` | sesi upload > 6 jam tanpa publish (cron) | – | `{ step }` | cron |

`step` memakai nilai yang sudah ada di `upload_sessions.step`:
`photo` → `caption` → `confirm`. Pertanyaan gender dan 18+ tetap di step
`confirm` (lihat `nsfw-18plus-plan.md`), jadi funnel dihitung dari
`meta.step` + `meta.gender`/`meta.nsfw` yang dikirim terpisah saat pertanyaan
dijawab.

Event yang **tidak** dibuat karena sudah ada di tabel lain: `reaction`,
`rating`, `comment`, `upload` (foto baru), `notification_sent`,
`leaderboard_sent`.

## 4. Pengiriman Event

### 4.1 Endpoint `POST /api/events`

`src/app/api/events/route.ts`:

```ts
const bodySchema = z.object({
  sessionId: z.string().min(8).max(64),
  events: z
    .array(
      z.object({
        name: z.enum(EVENT_NAMES),
        photoId: z.number().int().positive().optional(),
        meta: z.record(z.string(), z.union([z.string(), z.number(), z.boolean(), z.null()])).optional(),
      }),
    )
    .min(1)
    .max(20),
});
```

- Wajib session login (`getSessionUserId`), 401 kalau tidak ada. `userId`
  diambil dari cookie, **bukan** dari body.
- `photoId` diverifikasi ada di `photos` sebelum insert; yang tidak ada di-drop
  (jangan sampai insert gagal seluruh batch karena satu id salah).
- Rate limit in-memory per `userId`: maksimum 120 event / menit, sisanya dibuang
  diam-diam (balas `{ ok: true, dropped: n }`). pm2 jalan 1 instance fork, jadi
  Map biasa cukup; kalau nanti cluster, pindah ke Postgres atau Redis.
- Balas `204` dan jangan pernah melempar error ke client — analytics tidak boleh
  merusak UX.
- Insert satu statement `db.insert(events).values(rows)`.

### 4.2 Helper client `src/lib/analytics/track.ts`

```ts
track(name, { photoId, meta })  // masuk queue, flush kalau >= 10 atau 5 detik
flush()                          // dipanggil di pagehide via sendBeacon
```

Detail:

- `sessionId`: `crypto.randomUUID()` disimpan di `sessionStorage`
  (kunci `retpap_analytics_session`), jadi satu pembukaan app = satu session id.
  Sengaja **bukan** localStorage: user yang balik besok dihitung sebagai session
  baru, sementara identitas user tetap dari `userId`.
- Kirim pakai `fetch(..., { keepalive: true })`; saat `pagehide` pakai
  `navigator.sendBeacon` supaya tidak hilang ketika Mini App ditutup.
- Dedupe `photo_view`: simpan `Set<photoId>` di memori; satu foto dihitung
  sekali per session walaupun user bolak-balik.
- Kalau endpoint gagal, buang batch (jangan retry agresif) — hindari loop saat
  server down.

## 5. Membaca Angka

### 5.1 Query dashboard (fase 1, langsung ke `events`)

`src/lib/analytics/queries.ts`, semua pakai `sql` + `db.execute`:

```sql
-- DAU 30 hari terakhir
select date_trunc('day', created_at at time zone 'Asia/Jakarta')::date as day,
       count(distinct user_id) as users,
       count(*) filter (where name = 'app_open') as opens
from events
where created_at >= now() - interval '30 days'
group by 1 order by 1 desc;

-- funnel upload 7 hari
select meta->>'step' as step, count(distinct session_id) as sessions
from events
where name = 'upload_step' and created_at >= now() - interval '7 days'
group by 1;

-- konten teratas: view vs interaksi
select p.id, p.caption,
       count(*) filter (where e.name = 'photo_view') as views,
       (select count(*) from reactions r where r.photo_id = p.id) as reactions,
       (select count(*) from ratings r where r.photo_id = p.id) as ratings,
       (select count(*) from comments c where c.photo_id = p.id) as comments
from photos p
left join events e on e.photo_id = p.id and e.created_at >= now() - interval '7 days'
group by p.id order by views desc limit 20;

-- retensi D1: user yang app_open hari ini dan juga app_open besok
with first_day as (
  select user_id, min(date_trunc('day', created_at at time zone 'Asia/Jakarta')::date) as d0
  from events where name = 'app_open' and user_id is not null group by 1
)
select d0, count(*) as cohort,
       count(*) filter (where exists (
         select 1 from events e2
         where e2.user_id = first_day.user_id and e2.name = 'app_open'
           and date_trunc('day', e2.created_at at time zone 'Asia/Jakarta')::date = d0 + 1
       )) as d1
from first_day group by 1 order by 1 desc limit 30;
```

### 5.2 Pintu masuk owner

Tidak ada tautan apa pun dari halaman user biasa ke `/stats`. Satu-satunya jalan:

1. Owner mengirim `/stats` ke bot. Handler ada di `src/lib/bot/flow.ts`
   (`command === "stats"`), dijaga `user.id !== ownerTelegramId()` → balas
   "Command ini hanya untuk owner."
2. Bot membalas satu tombol URL ke `https://t.me/<bot>?startapp=stats`
   (`statsUrl()` di `src/lib/share.ts`). Sengaja URL `t.me` biasa, bukan
   `web_app`, supaya `startapp` ikut terbawa sebagai `start_param`.
3. Mini App boot seperti biasa: `POST /api/session` membuat cookie, lalu
   response berisi `owner: boolean`.
4. `pap-rater.tsx` hanya melakukan `router.push("/stats")` bila
   `sessionBody.owner && readStartTarget()?.type === "stats"`. User lain yang
   membuka link yang sama tetap di feed — parameter diabaikan.
5. `/stats` memeriksa ulang sesi dan `isOwner`; tanpa cookie atau bukan owner
   → 404.

Konsekuensi: membuka `https://bot.linkviu.my.id/stats` langsung dari browser
desktop atau dari chat mana pun tetap 404, karena tidak ada `initData` yang
bisa membuat cookie sesi.

### 5.3 Halaman `/stats`

`src/app/stats/page.tsx` — server component, tanpa chart library:

- Kartu: DAU/WAU/MAU, `app_open` hari ini, rasio `feed_loaded`/`app_open`,
  jumlah upload 7 hari (dari `photos.created_at`), rata-rata view per foto.
- Tabel: funnel upload (4 langkah + published + abandoned), funnel gate
  (shown → pass), top 20 foto (views, reaksi, rating, komentar), retensi D1/D7.
- Angka dihitung di server. Halaman memanggil `cookies()` sehingga otomatis
  dinamis; **jangan** menambah `export const dynamic = "force-dynamic"` karena
  `nextConfig.cacheComponents` menolaknya (build gagal).

Akses: **hanya owner, lewat sesi Mini App yang sudah ada.** Tidak ada env baru
dan tidak ada halaman login terpisah.

- `/stats` adalah server component yang memanggil `getSessionUserId()` lalu
  membandingkan `users.telegram_id` dengan `ownerTelegramId()`
  (`src/lib/bot/channel.ts`).
- Bukan owner atau belum punya cookie sesi → `notFound()` (404), bukan 401,
  supaya halaman tidak terlihat ada dari luar.
- Helper baru `isOwner(userId)` di `src/lib/analytics/queries.ts`:

```ts
export async function isOwner(userId: number): Promise<boolean> {
  const owner = ownerTelegramId();
  if (owner === null) return false;           // env kosong = tidak ada akses
  const [row] = await db
    .select({ telegramId: users.telegramId })
    .from(users)
    .where(eq(users.id, userId))
    .limit(1);
  return row?.telegramId === owner;
}
```

- Tidak ada `STATS_TOKEN`, tidak ada cookie tambahan. Konsekuensinya `/stats`
  hanya bisa dibuka dari dalam Telegram (Mini App), bukan browser desktop.
- Env `OWNER_TELEGRAM_ID` sudah terisi di lokal dan produksi, jadi tidak ada
  langkah konfigurasi baru saat deploy.

## 6. Angka Historis (tanpa event)

Sebelum deploy, metrik engagement tetap bisa dihitung dari tabel yang ada:

- upload per hari → `photos.created_at`
- reaksi/rating/komentar per hari → `reactions.created_at`, dst.
- user aktif kasar → `users.last_seen_at` (hanya ter-update saat app dibuka,
  jadi bukan pengganti `app_open`)
- leaderboard per periode → sudah ada di `getLeaderboard`

Yang tidak bisa direkonstruksi: impression (`photo_view`) dan funnel upload.
Itu alasan utama tabel `events` dibuat.

## 7. Privasi & Retensi

- Tidak menyimpan IP, User-Agent, `initData`, username, atau isi komentar di
  `events`. `meta` hanya enum/angka kecil.
- `sessionId` acak, tidak bisa dipakai untuk mengenali orang di luar aplikasi.
- Retensi: hapus `events` lebih tua dari 180 hari lewat cron harian
  (`delete from events where created_at < now() - interval '180 days'`
  dibatasi `limit 50000` per putaran supaya tidak mengunci tabel).
- User yang dihapus → `user_id` jadi null, event tetap ada sebagai angka
  agregat.
- Tidak ada cookie baru sama sekali. `sessionId` hanya di sessionStorage dan
  hilang saat tab ditutup. `/stats` memakai cookie sesi yang sudah ada.

## 10. Risiko

| Risiko | Mitigasi |
|---|---|
| `events` membengkak | Retensi 180 hari + fase 3 rollup |
| Event dobel saat React strict mode / remount | Dedupe `photo_view` per session + `app_open` hanya sekali per `sessionId` |
| Bot down / DB error merusak UX | Insert event dibungkus `try/catch`, tidak pernah menggagalkan request utama |
| Rate limit in-memory reset saat pm2 reload | Diterima; efeknya hanya beberapa event ekstra |
| Angka beda dengan Telegram stats | Wajar: `app_open` menghitung Mini App, bukan member channel |
